# 工坊规范：技能（Skill）

> 这份文档是工坊模式的内置操作手册（`spec_read` 返回的就是它），写给你（agent）照着做，不是用户输入。用户问起时可以概括，不要整篇复述。

## 1. 技能是什么，什么时候该造一个

技能就是一份 `SKILL.md`：一段 frontmatter（`name` + `description`）+ 一段正文，写清「某类任务该怎么做」。应用在**每轮对话开始**时把每个技能的名字与 description 列进系统提示词（只有几百字）；当任务和某条 description 对得上时，你（或其它轮次里的模型）用 `skill_read` 把正文读进来，再按正文执行。**正文平时不占上下文**，这是技能相对「写进提示词」的价值。

该造的情况：

- 同一套流程在多次对话里重复出现，而且步骤是稳定的。
- 流程依赖用户自己的约定：读哪个目录、引用怎么写、落盘到哪、输出什么格式。不写下来，每轮都要重新摸索，还容易走偏。

**不该**造的情况：

- 一次性的任务：这一轮直接做完就行。
- 两三句话能说清、内置工具本来就能完成的事。
- 与已有技能高度重合：先 `skill_list`，能改那一份就不要新建（重名是实打实的坑，见 §6）。

## 2. 工作台与发布流程

- 工作台根目录：`<工作区>/.hub/workshop/`。本模式下相对路径都以它为根。
- 技能草稿放在 `skills/<技能id>/SKILL.md`，附加文件放同一目录下（`references/`、`scripts/` 等）。
- 写完用 `skill_publish(dir)` 发布：把草稿目录装到工作区的正式位置 `<工作区>/.hub/skills/<技能id>/`，并重扫技能目录。`dir` 传相对工作台根的目录，例如 `skills/lecture-to-cards`。
- 发布是**覆盖式**的：内容改了再发一次即可，不必先删。
- 技能发布后属于**整个工作区**（所有主题都看得到），不分主题。要让某个主题忽略它，那是用户在界面上关开关的事，不是你能在文件里表达的。
- 迭代循环：`skill_publish` → `skill_list`（实时扫描，发布后立刻能看到）→ `skill_read(<id>)` 读回来核对 → 不对就改文件再发一次。

## 3. SKILL.md 的格式（解析规则，照实写别想象）

```markdown
---
name: 讲义转问答卡
description: 用户说「把这份讲义做成卡片」「帮我出几道自测题」时用。读讲义挑考点，建卡并写出处。
---

## 什么时候用
（这里才是正文）
```

- frontmatter 必须是**文件最开头**的一段 `---` … `---`，结束的 `---` 单独占一行。
- 只解析 `name`、`description` 两个键，**一行一个 `key: value`**，按行内第一个 `:` 切分；键名大小写不敏感；值两端的单引号/双引号会被去掉。
- 这不是完整 YAML：多行值（`description: |` 换行续写）、列表、嵌套对象都不会被解析。写 `|` 得到的就是一个字面量 `|`。description 必须写在同一行里。
- frontmatter 里以 `#` 开头的行会被当注释跳过，空行跳过。
- 没有 frontmatter（或没写结束的 `---`）时：`name` 退化为**目录名**，`description` 退化为正文里第一条非空、非 `#` 的行。能跑，但别依赖它。
- **技能 id = 技能目录名**；frontmatter 里的 `name` 只是显示名。
- 附带文件清单：技能目录下（最多 3 层）除 `SKILL.md` 以外的文件会被 `skill_read` 列出来；以 `.` 开头的目录和 `node_modules` 会被跳过。

## 4. description 怎么写

description 是模型判断「要不要加载这个技能」的**唯一依据**；而且系统提示词里只放它的**前 120 个字符**（`skill_list` 里能看到全文）。所以「什么时候用」必须在前 120 字里说完，做法要点可以放在后面。

好/坏对照：

- 坏：`description: 帮助你学习。` —— 空话，任何任务都对得上，等于没写。
- 好：`description: 用户说「把这份讲义做成卡片」「帮我出几道自测题」时用。读讲义挑考点，每张卡附出处。`

- 坏：`description: 这是一个把 Markdown 讲义整理成问答卡片的技能，它会先读原文，然后按考点拆分，再调用卡片工具……（触发条件写在第三句以后）` —— 前 120 字被截断后只剩铺垫，模型看不到触发时机。
- 好：把触发词放最前，做法放后：`description: 用户给了一份讲义/笔记并要求「做成卡片」「出自测题」时用；读原文 → 拆考点 → 建 basic/cloze 卡，source 填出处。`

- 坏：`description: 写代码、查资料、做总结的时候用。` —— 范围大到覆盖一切，加载与否全凭运气。
- 好：`description: 用户说「查 DOI / PMID」「把这批文献导出成 BibTeX」时用；先检索再落盘引用清单。`

写法要点：写「用户会说什么」+「对什么做事」+「产出什么」。可以列举触发词（用户的原话），不要写「提升效率」「智能化」这类形容词。

## 5. 正文怎么写

正文是给**另一个上下文里的模型**看的操作手册，不是给人读的散文。

- 结构建议（顺序照抄）：`## 什么时候用` → `## 步骤`（编号，每步写清做什么、用哪个工具、关键参数、判断标准）→ `## 输出格式` → `## 不要做`。
- **用真实工具名，写清参数**。本应用的工具有英文蛇形名字。常用的几个：文件 `fs_list` / `fs_read` / `fs_search` / `fs_write`；讲义检索 `kb_search`（`query`、`limit`）；写笔记 `note_create`（`title`、`content`、`tags`、`dir`、`topic`）；建卡 `card_create`（`front`、`back`、`kind`、`source`、`module`）；任务 `task_create` / `task_list` / `task_update`；演示页 `viewer_open`；导图 `mindmap_create`；记忆 `memory_write`。
  **不要编工具名。** 技能发布后会用在别的对话里，那边看不到你这里的推测，只会照着名字调用然后拿到「没有名为 X 的工具」。
- **路径写「相对主题目录」的相对路径**（`materials/ch1.pdf`、`notes/讲义.md`），并说明要操作别的主题时用 `topic` 参数。别写绝对路径（换机器、换工作区就失效）。
- **引用的附加文件要在正文里点名**：例如 `引用格式不清楚时读 references/引用格式.md`。`skill_read` 只给一份文件清单，不点名的文件不会被读。
- 读附加文件时要**拼上技能目录的完整路径**：内置 `fs_read` 的相对路径是相对主题目录解析的，不是相对技能目录。`skill_read` 的输出里带技能目录，照抄拼。
- 篇幅：正文 50–150 行。长内容拆到 `references/`（示例、对照表、模板），正文只留「什么时候去读它」。
- 语气：祈使句 + 编号 + 判断标准（「一句话只留一个考点」「正面要能独立看懂」）。不要写「请注意」「祝你好运」这类空话。

## 6. 命名与重名

- id 用短横线小写英文（`lecture-to-cards`）最省事；中文目录名也能用（扫描只看目录名，不要求 ASCII）。
- 目录名不能含 `< > : " / \ | ? *`，不要以空格或 `.` 结尾，不要用 Windows 保留名（CON、PRN、AUX、NUL、COM1…）。目录名太长会被文件系统截断，控制在 64 字符内。
- 一个目录只认一个 `SKILL.md`：不要在一个目录里塞两个技能。
- 发布前先 `skill_list` 查重。**重名时先扫到的胜出**，扫描顺序是：本主题私有 → 父主题私有 → 工作区 `.hub/skills`（你发布的位置）→ 用户目录 `~/.agents/skills` → 用户目录 `~/.learning-hub/skills` → 配置里的额外目录。
  也就是说：用户装的同名技能，在**某些主题**里可能盖掉你发布的这份。重名就换个 id，不要赌优先级。

## 7. 完整最小示例：讲义转问答卡

`skills/lecture-to-cards/SKILL.md`（这个技能只依赖内置工具，发布后在任何主题里都能照做）：

```markdown
---
name: 讲义转问答卡
description: 用户说「把这份讲义/这段笔记做成卡片」「帮我出几道自测题」「生成问答复习卡」时用。先读讲义拆考点，再建卡与自测笔记，每张卡附出处。
---

## 什么时候用
- 用户给了一份讲义、资料或笔记，要求产出「卡片 / 自测题 / 问答」。
- 用户说「复习不动了，帮我拆成能考的问法」。

## 步骤
1. **确认来源**。用 `fs_list` 看 `materials/`、`notes/` 里有什么（`depth` 默认 2），
   或从上下文判断用户指的是哪一份。要按主题检索用 `kb_search`，
   参数 `query`（多个词用空格分隔）；索引为空时它会自动建一次。
2. **读原文**。用 `fs_read` 读那一份（PDF 会自动提取文字）。一次读一章，不要吞整本。
   扫描件 PDF 提不出文字时会明确报错，这时请用户换文字版，不要硬猜内容。
3. **拆考点**。把内容拆成「一个能独立提问的点」：定义、公式、成立条件、易错边界。
   一句话只留一个考点；纯叙述性的段落不要硬做成卡。
4. **建卡**。用 `card_create` 逐张建，一次一张或传 `cards` 数组：
   - `front`：一个明确的问题或提示；完形卡则写整段带 `{{c1::挖空内容}}` 的文字，并传 `kind: "cloze"`。
   - `back`：简洁准确的答案（完形卡可留空）。
   - `source`：照抄来源，例如 `materials/ch1.pdf 第 12 页`。**页码照 `kb_search` 给的写，不要自己编。**
   - `module`：本章或子话题名，方便按块复习。
5. **写自测笔记**。用 `note_create` 存一份 `title: "<来源名> 自测题"` 的笔记：
   正面抄成题，答案放下一行，供用户通读。
6. **汇报**：建了几张卡、覆盖哪几个考点、哪几处因为讲义没讲清所以没出卡（并指出在哪一页）。

## 输出格式
- 卡片正面：一个问句，或一句待填空的原句。不要「以下哪个」这种选项。
- 卡片背面：先结论，再一句理由；公式用 LaTeX（`$...$`）。

## 不要做
- 不要没读讲义就凭印象出卡。
- 不要把多个考点塞进一张卡。
- 不要把章节名当页码写（确实要指章节时才写章节名）。
```

## 8. 发布后怎么确认它没问题

1. `skill_publish("skills/lecture-to-cards")`。
2. `skill_list`：应当立刻出现，且名字与 description 完整（这是实时扫描，不等下一轮）。
3. `skill_read("lecture-to-cards")`：读回来的正文应当是完整的、frontmatter 没漏；文件清单一节里应当出现你写的每一个 `references/…`。
4. 生效的前提（不是你能改的）：技能总开关开着，且这个技能没被禁用（全局 / 本主题 / 父主题任意一处禁掉都会让它不出现）。
5. 系统提示词里的技能清单是每轮开始时装好的，所以「作为提示词的一部分」要到**下一轮**才更新；`skill_list` 不受影响。
6. 有问题就改工作台里的文件，再 `skill_publish` 一次。

## 9. 常见错误清单

1. **description 太泛或太长**：前 120 字里看不到「什么时候用」，等于这个技能不会被加载。
2. **正文写成散文**：没有编号步骤、没说用哪个工具，模型读完还是不知道先做什么。
3. **假设了不存在的工具**：写「用 read_file 读」「调用 create_cards」，实际只有 `fs_read` / `card_create`。发布前对着系统提示词的工具清单核一遍。
4. **引用了不存在的文件**：正文让读 `references/格式.md` 但目录里没有它。`skill_read` 的文件清单里没有，就是没有。
5. **重复已有技能**：重名不报错，但可能被先扫到的同名技能盖掉，你会以为「发布了却没生效」。
6. **用了完整 YAML 的写法**：`description: |`、多行续写、列表 —— 解析器只认单行 `key: value`。
7. **忘了 `---` 或把 frontmatter 放到正文中间**：整份文件被当正文，name 退化成目录名、description 退化成正文第一行。
8. **写绝对路径**：`E:\学习中枢\...` 这类路径换机器/换工作区即失效；统一写主题内相对路径。
9. **把技能当配置用**：技能只能写「流程与文本」，改不了开关、权限、模型、目录结构。需要改这些，请让用户在设置里操作。
